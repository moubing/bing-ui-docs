# bing-ui 文档统一维护与 AI 读取改造交接

记录日期：2026-09-05。

本文保留最初的改造方案及阶段记录。截至 2026-09-06，现有 33 个组件页均已完成 Markdown、共享 API、完整 Vue 示例和 AI 导出迁移；Form/FormItem 之后的组件分别提交。最新覆盖范围与验证结果见[组件迁移记录](./component-migration-progress.md)及 `public/ai/manifest.json`。下文试点阶段描述用于追溯，不应替代最新记录。历史快照、远程发布和使用方入口调整尚未实施。

## 1. 要解决的问题

`requirement-board` 使用 bing-ui 时，曾重复实现组件库已有的分类切换和分页，也没有正确接入审批表单校验。应用侧已经修复这些问题，但把组件用法复制到各业务项目，会产生新的维护负担：组件库更新后，每个项目都要同步自己的说明。

用户希望把组件知识集中维护在 `bing-ui-docs`，让网站和 AI 共用可靠的文档。业务项目只保留文档入口与业务自身的规则，不再复制通用组件 API。

用户特别关心现有体验：以前尝试过 MDC，效果不理想。此次改造必须以“现有视觉与交互基本不变”为验收目标，不能为了 Markdown 降低网站的可用性。

## 3. 已明确的诉求与建议基线

用户明确的诉求：

- 组件说明集中维护，多个使用方不各自维护一套 API 文档。
- 现有交互文档能继续供人使用，同时让 AI 容易查到准确用法。
- 改造后视觉、参数调节、实时预览和其他交互体验基本不变。
- 本地与远程文档都要有清楚的读取方式。

此前提出的建议，实施时应验证可行性：

- 说明使用 Markdown，交互示例保留 Vue；网站和 AI 导出共用内容、API 数据和示例源码。
- 先验证 Markdown 渲染适配，优先评估 Comark 的 Nuxt 集成，不预设必须引入完整 Nuxt Content；最终接入方式以 Form/FormItem 的结构、视觉和交互验证为准。
- 增加简短的 `llms.txt` 索引，按组件提供可直接读取的 Markdown。
- 先匹配组件版本，再选择本地或远程来源；同级 clone 是便捷约定，不是强制前置条件。
- 先迁移 Form 与紧密关联的 FormItem，通过对照验证后逐步推广。

截至 2026-09-05 本次评审核对，MDC 官方已声明正在弃用 `@nuxtjs/mdc`，推荐后继项目 Comark；官方 Nuxt 集成包为 `@comark/nuxt`。新接入优先评估 Comark，不再以安装旧 MDC 模块作为前置步骤。官方说明见第 12 节，实施时仍需核对当前版本的兼容性。

Markdown 渲染器是内容组织工具，统一维护和保留现有体验才是目标。如果试点发现所选渲染器必须牺牲现有交互才能工作，应说明具体问题，并评估保留 Vue 页面、抽取共享文档内容和数据后导出 Markdown 的方案。不要为了采用某个渲染器而重写整个站点。

- `package.json` 声明 `@moubing/bing-ui: ^0.5.3`，本次评审核对的已安装版本为 `0.5.3`；没有安装 Nuxt Content、MDC 或 Comark。

## 5. 内容如何只维护一份

建议按职责抽取：

| 内容 | 维护来源 | 网站与 AI 如何使用 |
| --- | --- | --- |
| 组件用途、使用规则、注意事项 | Markdown | 网站渲染，AI 直接读取或读取导出版本 |
| props、事件、插槽、公开方法 | 一份结构化数据或规范化文档内容 | 同时生成网站 API 表与 Markdown API 表 |
| 示例运行逻辑 | Vue 示例组件 | 网站直接运行；AI 导出包含相关源码或明确的源码链接 |
| 随参数变化的代码示例 | 共用代码生成逻辑和默认参数 | 网站动态展示；AI 导出一份完整、可理解的默认用法 |
| 组件索引、版本信息 | 清单或生成脚本 | 生成统一入口，避免多处手工维护链接 |

不建议保留 Vue 中完整的旧文字说明，同时人工再写一套同义 Markdown。抽取一个组件后，必须明确哪份是编辑源、哪些是生成结果。

API 类型可以帮助检查 props 和事件参数，但默认行为、校验时机等语义仍需要人工描述并验证。不要承诺仅凭 `.d.ts` 就能自动生成完整可靠的使用说明。

给 AI 的导出不能只有 `::form-playground` 或 `<FormDemo />`。至少应包含用途、基本用法、完整的相关代码、API 和行为约束。与示例运行有关的 import、model 和 schema 不应遗漏。无需把主题切换、页面装饰和整个 playground 的控制逻辑全部灌进基础示例。

可参考的目录组织如下，实际名称由实现决定：

```text
content/components/form.md             # 说明来源
shared/docs/form.ts                     # 共用 API 数据、示例元信息
app/components/examples/form/           # 交互示例
app/components/content/                 # 必要的 Markdown 渲染适配组件
scripts/                               # 文档导出与检查
public/llms.txt                         # 生成的统一索引
public/ai/manifest.json                 # 生成的版本与组件清单
public/ai/components/form.md            # 生成的纯 Markdown
```

这是建议结构，不是要求创建每一层。如果选择输出到 `public/`，Nuxt 静态文件 URL 通常不会包含 `/public`，链接应按实际运行结果验证。

## 6. 保留当前体验的实施要求

保留原有页面外壳、URL、主题、导航、滚动组件、代码展示组件和页面过渡。Markdown 主要负责说明和示例的位置，状态与事件仍由 Vue 组件管理。

Form 试点应尽可能直接抽出原有交互逻辑，保留参数调节、实时预览、动态代码及验证结果。不要把交互状态硬塞进 Markdown，也不要因拆组件造成原本共享的状态失联。

已经发现的具体依赖：

- `app/layouts/docs.vue` 使用 `.doc-page h1[id], .doc-page h2[id], .doc-page h3[id], .doc-page section[id]` 收集目录；保留稳定的 ID、层级和既有深链接，避免自动生成的标题锚点造成重复目录项。
- `main.css` 中存在 `.doc-page > h1 + p`、`.doc-section > h2:first-child`、`.doc-page section > .bing-code-block` 等直接子元素选择器。渲染器增加容器或段落标签后，需要逐项核对实际 DOM 和排版。
- `.doc-example` 及其子类承担预览和控制区布局；继续沿用合适的结构和响应式行为。
- `ClientOnly`、异步内容加载和示例组件挂载顺序可能影响首屏、目录收集、页面缓存与状态保持，必须通过浏览器验证。
- 代码高亮、复制、代码分组等继续复用既有组件和样式，避免引入第二套外观。

优先控制内容渲染的结构，使其符合现有页面约定。如果确实需要调整 CSS 或目录逻辑，改动应保持兼容未迁移页面，不能为了试点牺牲其他组件页。

“基本不变”需要对照证据，不等于只确认页面没有报错。不要在没有运行和对比前宣称无损迁移。

## 7. AI 入口、本地与远程读取

统一入口应简短，包含库名称、文档适用版本、接入说明、组件名称及文档链接。按需读取单个组件，不要求每次加载全部组件正文。`llms.txt` 是入口约定，不会自动保证所有 AI 工具都读取它；业务项目仍需要一条明确的读取指引。

建议读取顺序：

1. 确认使用方实际安装的 `@moubing/bing-ui` 版本；不能只把 `package.json` 中的版本范围当作安装版本。
2. 检查约定的本地 docs 位置，例如同级 `../bing-ui-docs`，并核对其文档版本。读取文件无需安装依赖或启动站点。
3. 本地存在对应版本快照时直接读取；不要为了查看旧版而切换或覆盖用户当前 checkout，可以用只读 Git 操作读取已存在的历史版本。
4. 本地没有匹配版本时，读取远程对应版本的索引、Markdown 或原始文件。
5. 无法取得匹配文档时明确说明，再用已安装包的类型和实现核对；不能静默拿最新版当旧版文档。

同级 clone 只是推荐布局，不应成为所有开发者的强制要求。不要每次读取都自动 `git pull`，也不要因本地有目录就忽略版本不一致。

远程仓库首页可以保留为总入口，但要提供进一步能定位文档的固定路径或索引。当前没有已确认可用的 AI 文档地址，实施时不能把设想的 raw URL 当作已上线链接。

## 8. 文档版本与维护流程

文档版本对应组件库版本，而不是 docs 项目自身随意递增的版本。先记录实际验证过的库版本；只有经过验证，才声明更宽的兼容范围。

实现可使用发布清单和对应文档快照，后续通过 tag 或版本目录保留历史。命名方式要简单明确，并记录从组件版本到文档快照的映射，不能假定永远读取最新 `main`。

这里区分两件事：

- **文件纳入 Git 版本控制**：说明源、API 数据、示例源码和生成的 AI Markdown 一起保存到仓库。生成结果随对应源码更新，读取方 clone 后即可查阅。这不要求另建版本管理服务。
- **按组件版本读取文档**：用清单记录组件版本与文档快照的对应关系，避免使用方把新版用法套到旧包上。这需要版本索引和快照生成、检查逻辑。

首版建议采用以下最小方案，具体字段和路径在实现时确定：

1. 只覆盖实际验证过的 `0.5.3`，不补造旧版本文档，也不自动声明整个兼容范围。
2. 清单记录包名、`packageVersion`、`docsRevision`、组件文档路径及迁移状态。`docsRevision` 用于区分同一组件版本下的文档发布修订，例如 `0.5.3 / r1`、`0.5.3 / r2`。
3. 日常编辑由 Git 跟踪；同一组件版本的文档纠错发布时增加文档修订号，组件版本保持不变。组件库升级后，先核对行为和示例，再声明新版本的文档支持。导出检查应发现安装版本与声明版本不一致，不能自动改写声明来掩盖未验证的升级。
4. 发布时通过固定 Git 提交/tag 或版本目录保留快照，并在索引中记录实际可读取的位置；已经发布的快照不覆盖。历史快照至少保留纯 Markdown 和相关示例源码，网页若只展示当前版本，应明确标注其版本。首版不要求让每个历史版本都运行一套交互文档站。
5. 发布新版本后继续保留已有静态快照；没有匹配版本时明确提示缺失。当前范围先验收本地读取与可发布产物，真实远程入口在发布后验证。

版本管理的主要持续成本是确认组件行为、API 和示例与声明版本一致；索引和快照脚本只负责保存、定位及一致性检查，不能替代用法验证。

需要在 docs 仓库说明日常维护流程：

1. 组件行为变化后，修改其统一说明、API 数据及示例源。
2. 运行导出，让网站和 AI 文档使用同一份更新后的信息。
3. 检查生成结果、链接、版本元信息以及关键示例。
4. 发布时关联对应版本快照；实际 Git tag、推送和部署仍由用户明确安排。

生成脚本应可重复运行，结果确定，并能检查是否存在未更新的生成内容。为了让只有 clone、没有运行环境的读取方也能直接查阅，需明确哪些导出文件随仓库保存，哪些在构建时生成。不能一面承诺 clone 后直接读取，一面把全部 AI 文档只留在尚未执行的构建产物里。

把文档快照随 npm 包分发是后续可选优化，本次不以修改组件库发布流水线为前提，也不为此引入新的 MCP 服务或强制安装插件。

### 第一阶段：基线与 Form 试点

1. 检查工作区、项目规则和依赖，保存 Form/FormItem 的改造前截图与交互基线。
2. 验证 Markdown 渲染的最小适配方式，优先评估 Comark；先用包含标题、说明、交互示例、代码块和 API 表的一段完整内容，确认可保留现有结构和样式。
3. 抽取 Form/FormItem 的说明、API 数据与 Vue 示例，保持原 URL。
4. 生成统一索引、版本元信息和这两个组件的 AI Markdown。
5. 完成截图与交互对照，修复由迁移引入的差异。
6. 写清使用方读取约定、文档生成命令和维护流程。

第一阶段应产出可运行、可验证的完整路径，不能只交付一个文档目录或空索引。

### 第二阶段：推广已有组件

试点通过后，按相同规则逐步迁移已有组件。优先覆盖 Tabs、Table、CheckboxGroup、RadioGroup、Textarea 等实际接入中容易漏用或用错的组件，再覆盖其他页面。迁移顺序可调整，但不要一次性替换整个站点后才验证体验。

统一索引可以在过渡期指向未迁移组件的现有 Vue 文档，必须明确标记来源和迁移状态，不能伪称所有条目都有纯 Markdown。

最终目标是所有已有组件都能通过统一入口找到可靠用法。阶段性交付必须列出已迁移与尚未迁移部分，不能把 Form 试点等同于全站完成。

当统一入口稳定后，提供业务项目可直接使用的短说明模板。`requirement-board/docs/bing-ui.md` 后续可收缩为入口和业务约束；不能在替代入口还不能用时先删除现有说明。

## 10. 验收要求

| 验证项 | 应达到的结果 |
| --- | --- |
| 内容一致性 | 改一处说明/API/示例源后，网站与 AI 导出能同步变化，没有另一份人工维护的副本 |
| 桌面与手机布局 | 字体、间距、配色、预览区与控制区布局基本一致，无新增横向溢出 |
| 主题 | light/dark/system 的正文、示例和浮层表现保持一致 |
| Form 交互 | 调节布局、标签位置、尺寸、列数、间距、禁用、校验时机后，预览与代码仍同步 |
| Form 校验 | 空值/错误值/合法值提交反馈正确，异步校验、字段校验、清错和重置方法可用 |
| FormItem | 必填标记、帮助与错误切换、跨度与插槽示例保持可用 |
| 代码展示 | 动态代码、复制及相关代码分组行为正确 |
| 路由与目录 | 既有 URL 和锚点可用，目录无重复，跳转定位与高亮正确 |
| 状态与滚动 | 页面往返后的示例状态和滚动恢复与改造前一致 |
| 未迁移页面 | 共用布局或 CSS 改动没有破坏其他组件文档 |
| AI 读取 | 只给统一入口，能找到指定组件及其正确用法，无需启动交互页面 |
| 版本选择 | 本地匹配、本地不匹配、仅远程可用、匹配文档缺失等情况均有明确处理 |
| 导出质量 | 内容包含可理解的代码和 API，生成可重复，无失效链接或未展开的示例占位 |

可用这些具体问题检查 AI 导出是否足够完整：

- `BingFormItem.required` 是否会自动校验？
- `BingForm` 校验失败时是否仍触发 `submit`，回调应如何阻止业务提交？
- 一个角色数组至少选一项，应如何用 schema、FormItem 和 CheckboxGroup 接线？
- `BingTable` 如何接服务端分页，是否还需要使用方手写分页栏？
- 分类切换组件的实际导出名称是什么，如何绑定当前值？

这些答案要以对应版本实际行为为准。通用文档不能代替业务规则，例如“批准必须选择角色”仍由业务应用决定。

## 11. 执行约束

- 开始工作时检查相关仓库的 `git status --short`，保留用户现有改动；读取适用的 `AGENTS.md`。
- 手动编辑使用 `apply_patch`，不直接修改 `node_modules`、`.nuxt`、`.output` 等内容。
- 使用 pnpm 与现有锁文件；新增脚本和依赖要同步中文 README。
- 浏览器测试默认无头。若内置 Chromium 不可用，可以临时使用系统 Chrome/Edge 的无头模式，不提交机器专属路径。仅当无头验证确实无法完成时，说明原因并取得用户明确同意后使用可见浏览器。
- 不占用或停止用户已有服务。`requirement-board` 当前使用过本地 3000 端口，测试 docs 前检查端口，必要时使用另一个空闲端口。
- 完成后关闭自己启动的临时浏览器与服务，清理临时文件；必要的测试结论记录在交付说明中。
- 不机械地运行完整构建。先做相称的类型/导出检查与浏览器验证；涉及 SSR、静态输出或构建资源路径时，再执行必要的构建或生成验证。
- 不自动提交、推送、创建 PR、打发布 tag、发 npm 包或部署；这份交接不授权上述动作。
- 本任务不需要改动数据库、密钥、服务器配置或现有业务权限。

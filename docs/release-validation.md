## 后续发布步骤

1. 通过官方 registry 重新查询发布版本，核对实际安装包与 CHANGELOG。同步精确依赖及 `docsVersion`；仅改文档时递增 `docsRevision`。
2. 阅读从上次目标至本次版本的每一条变更；更新升级指南中的调用方检查、新能力及修复。若没有用户侧迁移，在 `releaseReview` 和指南中明确写“无需迁移”并链接 CHANGELOG。
3. 检查首页、快速开始、组件目录、两仓库 README 及受影响组件的正文 / API / 预览 / 独立示例。更新 `releaseReview` 的人工核对版本、日期和结论，先将未完成的页面 `verified` 设为 false；有验收记录后才设为 true。
4. 运行导出、检查、受影响示例类型检查与无头验证。`docs:check` 会拒绝遗漏人工核对基线、旧推荐版本、失效章节或过期产物；`build` / `generate` 也会先执行该检查。README 的两个生成区块由导出器维护，不手工改数；历史版本编号可以保留。
5. 两仓库同步时显式传入组件库路径，工具只读取，不猜测同级目录、不改本机配置。组件库 README 的当前版本、安装命令和文档页统计须与文档站一致。
6. 部署完成后，传入实际站点 origin 重新读取首页、快速开始、升级页、AI 指南、llms.txt 与 manifest。命令通过后将实际版本、修订、时间、部署提交和结果补入本记录；Jenkins 成功或本地源码一致不能代替这一步。

```powershell
pnpm docs:export
pnpm docs:check
pnpm typecheck:ai-examples upgrade

# 替换为当前已核对的组件库路径；不提交机器专属路径。
pnpm docs:check-release --library-dir <组件库绝对路径>

# 部署后替换为实际站点的 origin；该命令只读，不触发发布。
pnpm docs:check-release --site <线上站点的origin>
```

未填写或核对失败时，保持“待部署 / 待核对”，不要把目标版本复制为已部署版本。`manifest.siteReview` 中的验证仅对应记录的 packageVersion / docsRevision，不宣称未来版本已经通过。
